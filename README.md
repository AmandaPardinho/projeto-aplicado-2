## 🇬🇧 English

Repository containing the code and supporting materials developed for the **Applied Project II** course.

### About the project

A **customer service automation system for a Pilates Studio** — a Python backend (FastAPI) integrated with Supabase (PostgreSQL), featuring a conversational WhatsApp agent and workflow orchestration with n8n.

### Stack

- **Backend:** Python 3.12+ · FastAPI · Pydantic v2 · Uvicorn
- **Database:** Supabase (PostgreSQL 17) — accessed via `supabase-py`
- **Workflow orchestration:** n8n
- **Messaging:** WhatsApp Business API / Evolution API
- **Infrastructure:** AWS

### Architecture

The backend follows a layered separation (DDD lite):

| Layer | Folder | Responsibility |
|---|---|---|
| **API** | `app/api/` | FastAPI routers — receive HTTP requests, delegate to the service, return the response |
| **Service** | `app/services/` | Business rules — orchestrate the repository, validate complex rules, prepare data |
| **Repository** | `app/repositories/` | The only layer that talks to Supabase (wraps the SDK) |
| **Schemas (DTOs)** | `app/schemas/` | Pydantic models — database entity + Create/Read/Update DTOs |
| **Core** | `app/core/` | Configuration (`.env`), reusable validators (CPF, WhatsApp) |

Applied patterns:
- **Soft-delete** on every entity (`is_active` + `deleted_at`) — LGPD compliance and auditing.
- **Client reactivation** via `PUT {is_active: true}` (clears `deleted_at` in the service). When re-registering a CPF that already exists, the `POST` returns **409** carrying the existing student's data (`conflict_with`: id, name, `is_active`), and the frontend offers reactivation — an **explicit decision** by the front desk (the student may have provided the CPF to request deletion under LGPD, not to return).
- **`created_at` immutability** via a PostgreSQL trigger (rule in the database, not in the app).
- **Two-layer validation:** `CHECK` in the database (source of truth) + Enum/Pydantic in the app (UX and fail-fast).

### Initial setup

#### 1. Clone and install dependencies

```bash
git clone https://github.com/AmandaPardinho/projeto-aplicado-2.git
cd projeto-aplicado-2

python -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
```

#### 2. Configure environment variables

Copy the template and fill it in with your real values:

```bash
cp .env.example .env
```

Required variables:

| Variable | Description | Source (Supabase Dashboard) |
|----------|-------------|----------------------------|
| `SUPABASE_URL` | Project URL | Settings → API → Project URL |
| `SUPABASE_ANON_KEY` | Public key (frontend / API with RLS) | Settings → API → `anon` `public` |
| `SUPABASE_KEY` | Admin key (privileged backend) | Settings → API → `service_role` |
| `SUPABASE_DB_HOST` | Database host for direct connection (pg_dump) | Settings → Database → Direct connection |
| `SUPABASE_DB_PASSWORD` | PostgreSQL database password | Settings → Database → Database password |

> ⚠️ **Never expose `SUPABASE_KEY` (service_role) in the frontend** — it bypasses RLS and has full access to the database.

> ⚠️ If the password contains special characters such as `$`, wrap the value in **single quotes** in `.env`:
> ```
> SUPABASE_DB_PASSWORD='senha$com$cifrao'
> ```

#### 3. Run the application

```bash
uvicorn app.main:app --reload
```

Access:
- **API:** http://localhost:8000
- **Swagger UI:** http://localhost:8000/docs
- **ReDoc:** http://localhost:8000/redoc

#### Clients (`/clients`)

| Method | Route | Description |
|---|---|---|
| POST | `/clients` | Create a new client (duplicate CPF → **409** with `conflict_with`) |
| GET | `/clients` | List all clients |
| GET | `/clients/by-cpf/{cpf}` | Find a client by CPF (finds it even if inactive) |

**DTO validation rules:**
- `cpf`: accepts a mask — 11 digits verified by the official Receita algorithm.
- `whatsapp_number`: accepts a mask — BR number with a valid area code and mobile (9 after the area code), normalized to the format `5511987654321`.
- `client_status`: enum of 3 values (`prospect`, `active`, `inactive`) — mirrors the database `CHECK`.

> **Reactivation:** if the `POST` hits a CPF that already exists, the **409** response includes
> `conflict_with` (`id`, `name`, `is_active`) of the existing student. The frontend uses this to
> offer reactivation (`PUT {is_active: true}`) instead of just blocking — reactivation is always
> a front-desk decision.

#### Client Plans (`/client_plans`)

The enrollment — links a client to a plan.

| Method | Route | Description |
|---|---|---|
| POST | `/client_plans` | Create an enrollment (one active plan per client → **409** with `conflict_with`) |
| GET | `/client_plans` | List all enrollments |
| GET | `/client_plans/{id}` | Find an enrollment by ID |
| PUT | `/client_plans/{id}` | Update enrollment fields (partial update; `is_active=true` reactivates) |
| DELETE | `/client_plans/{id}` | Soft-delete |

**DTO validation rules:**
- `client_id` / `plan_id`: both must exist (otherwise **404**).
- `end_date`: derived in the service as `start_date + 1 year` (not user-provided).
- `start_date`: optional (defaults to today) and **immutable** after creation (PostgreSQL trigger).
- `renewal_date`: manual (empty on the first enrollment).
- One active plan per client (partial `UNIQUE` index `WHERE is_active`) → **409** with `conflict_with`, which enables the plan-switch flow.

### Database schema management

The full database DDL (tables, triggers, functions) is versioned in `database/migrations/` and generated automatically by the `dump_schema.sh` script.

#### Prerequisites

- **`pg_dump`** installed on the system:
  ```bash
  # Ubuntu/Debian/Mint
  sudo apt install postgresql-client

  # Verify the installation
  pg_dump --version
  ```
- `SUPABASE_DB_HOST` and `SUPABASE_DB_PASSWORD` variables configured in `.env`.

> ℹ️ The `pg_dump` version must be **equal to or greater than** the Postgres version on Supabase (currently 17). If your distro ships an older version, install from the PGDG repository (apt.postgresql.org).

#### Running the schema dump

From the project root:

```bash
# Grant execute permission (first time only)
chmod +x database/scripts/dump_schema.sh

# Run the dump
./database/scripts/dump_schema.sh
```

The script:
1. Reads the credentials from `.env`.
2. Connects to Supabase via port 5432 (Direct connection).
3. Generates a SQL file with the entire structure of the `public` schema (no data).
4. Saves it to `database/migrations/<timestamp>_schema.sql`.
5. Prints a summary with the count of tables, triggers, and functions.

#### When to run it

Whenever the database structure changes:
- Creating/altering tables
- Adding/modifying triggers or functions
- Changing constraints

After generating the dump, commit the generated file to version the schema's evolution.

```bash
git add database/migrations/
git commit -m "feat(db): update schema dump after <description of the change>"
```

A partir da raiz do projeto:

Sempre que houver mudanças na estrutura do banco:
- Criação/alteração de tabelas
- Adição/modificação de triggers ou funções

Após gerar o dump, faça commit do arquivo gerado para versionar a evolução do schema.
